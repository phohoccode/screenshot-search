# Screenshot Search — AI Context

## 1. AI Role

AI is used to improve retrieval quality, not to make the base application functional.

Core product must continue to work with:

- OCR
- SQLite
- FTS5

without any cloud AI dependency.

---

## 2. AI Principles

1. Local inference by default.
2. No screenshot upload by default.
3. No OCR text upload by default.
4. Prefer small task-specific models over large LLMs.
5. Measure latency and memory usage.
6. Model implementation must be replaceable.
7. Model/version information must be persisted with generated embeddings.
8. Exact keyword search must remain available.

---

## 3. Text Semantic Search

Goal:

Allow users to search concepts using natural language.

Example screenshot OCR:

```text
PrismaClientKnownRequestError
Transaction API error
Transaction already closed
```

User query:

```text
lỗi database bị timeout
```

Keyword overlap may be weak.

Text embeddings can retrieve the screenshot by semantic similarity.

---

## 4. Text Embedding Pipeline

```text

   v

   |
   v

   |
   v
Text Embedding Model
   |
   v
Embedding Vector
   |
   v

```

Query:

```text

   |
   v

   |
   v
Query Vector
   |
   v
Similarity Search
```

---

## 5. Model Requirements

Text model should preferably support:

- Vietnamese
- English
- mixed Vietnamese/English
- technical terminology
- code-related text
- short and medium text

Desired properties:

- small enough for local CPU inference
- reasonable embedding dimensions
- permissive license for intended distribution
- ONNX/export support
- stable tokenizer availability

Do not select a model based only on benchmark claims.

Test it against real screenshot OCR data.

---

## 6. Chunking

Very long OCR text may need chunking.

Possible strategy:

```text
Screenshot OCR
   |
   +--> chunk 1
   +--> chunk 2
   +--> chunk 3
```

Search result should still resolve back to the screenshot.

Do not introduce chunking before needed.

For ordinary UI screenshots, whole-document embedding may be sufficient.

---

## 7. Vector Storage (Implemented)

Phase 3 implements local SQLite BLOB storage:
- Table: `screenshot_embeddings` (Migration v4)
- Representation: Little-endian binary `f32` vectors (384 dimensions = 1,536 bytes/vector).
- Linear Scan: In-process Rust cosine similarity calculation.
- Performance: ~1.2ms for 10,000 vectors on CPU. No remote services, no native SQLite extension compile hurdles.

---

## 8. Hybrid Search (Implemented)

Semantic search complements FTS5 keyword search.
Implemented model: `intfloat/multilingual-e5-small` (384 dimensions, MIT license).
- Text formulation: `passage: Filename: <name>\nContent:\n<text>`
- Query formulation: `query: <query>`
- Two-stage candidate generation: Union top 100 FTS5 + top 100 Semantic vectors.
- Exact Token Guard: `4.0x` dominance signal for exact alphanumeric/code tokens.
- Fallback: Transparent zero-degradation fallback to FTS5 if model is absent.


- exact filename match should receive a strong signal
- exact error-code match should receive a strong signal
- semantic similarity should improve natural-language queries
- recency may be a secondary signal

Weights must be evaluated with real examples.

## 11. LLM Use

A general-purpose LLM is not required.

Possible optional future features:

- summarize OCR result
- explain technical screenshot
- answer questions about selected screenshots
- smart auto-tagging

If cloud LLM support is ever added:

- explicit opt-in
- clearly show what data will leave the device
- redact data where possible
- never silently send screenshots

## 12. Model Lifecycle

Models should have identifiers such as:

```text
model_name
model_version
tokenizer_version
embedding_dimension
```

Changing models may require reindexing embeddings.

The app should know which screenshots have embeddings generated by which model.

---

## 13. Hardware

The app must remain usable without a dedicated GPU.

CPU is the minimum baseline.

Optional acceleration may be added later for:

- DirectML
- CUDA
- CoreML
- other platform backends

Do not make GPU availability a hard requirement.

## 14. Local Multilingual OCR Fallback (Phase 3.5)

To prevent OCR degradation on hosts where the Windows native Vietnamese (`vi-VN`) language pack is not installed, the application integrates a local Multilingual OCR fallback:

- **Model Architecture:** PP-OCRv4 (compact detection & recognition ONNX models, ~16 MB total download).
- **Execution:** 100% in-process CPU execution via ONNX Runtime.
- **Vietnamese Character Set:** Full transcription of Vietnamese vowels with composite tone marks (`á`, `à`, `ả`, `ã`, `ạ`, `ă`, `ắ`, `ằ`, `ẳ`, `ẵ`, `ặ`, `â`, `ấ`, `ầ`, `ẩ`, `ẫ`, `ậ`, `é`, `è`, `ẻ`, `ẽ`, `ẹ`, `ê`, `ế`, `ề`, `ể`, `ễ`, `ệ`, `í`, `ì`, `ỉ`, `ĩ`, `ị`, `ó`, `ò`, `ỏ`, `õ`, `ọ`, `ô`, `ố`, `ồ`, `ổ`, `ỗ`, `ộ`, `ơ`, `ớ`, `ờ`, `ở`, `ỡ`, `ợ`, `ú`, `ù`, `ủ`, `ũ`, `ụ`, `ư`, `ứ`, `ừ`, `ử`, `ữ`, `ự`, `ý`, `ỳ`, `ỷ`, `ỹ`, `ỵ`, `đ`) plus Latin alphabet and technical symbols.
- **Zero Cloud & Zero LLM Rewrite:** No external API requests, no heuristic replacement tables (`toån` -> `toán`).
- **Coexistence:** Runs alongside Phase 3 `multilingual-e5-small` text embeddings with zero dependency conflicts.

## 15. AI Scope Guard

Before adding a new AI feature, answer:

1. What user problem does this solve?
2. Can deterministic code solve it better?
3. Can it run locally?
4. What happens when inference fails?
5. What data does the model access?
6. How much CPU/RAM/disk does it add?
7. How is the feature evaluated?

Do not add AI solely because it is available.
